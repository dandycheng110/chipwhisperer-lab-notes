# 演進式架構實戰：從單體、微服務到 Docker、Kubernetes 與 AI 雲原生轉型

> 以「淘寶架構演變簡史」為情境載體，重現從 **100 併發** 到 **千萬級併發** 的 14 次架構演進。
> 不先拋概念，先給痛點：讓你在一層層堆疊的運維地獄裡，**自然長出**「這裡非用容器與編排不可」的需求。

---

## 這本書想解決什麼問題

AI 會寫程式之後，一行一行敲 code 的價值正在稀釋，真正稀缺的變成兩件事：

1. **確定系統的目標與樣子** —— 需求分析師的活。
2. **決定系統長成什麼形狀** —— 架構師的活。

而這個年代要決定架構，繞不開 Docker 與 Kubernetes；更繞不開一個更難的問題：
**為什麼大型系統「非得」長成那個樣子？**

直接讀 K8s 官方文件的問題在於：它只告訴你 `Deployment` 有哪些欄位，不會告訴你
「當年是什麼樣的痛，逼得人類發明了 Deployment」。**沒有痛點的知識記不住，也用不出來。**

所以這本書反過來寫：**問題驅動（Problem-Driven）**。
每一章都從「現在流量長成這樣、機器叫成這樣、半夜被 call 成這樣」開始，
先讓你痛，再讓解法自己浮出來。

---

## 重要聲明

- 本書以淘寶為 **教學模型**，不是淘寶的真實內部架構路徑。
  真實系統的演進遠比任何教材混亂，且大量細節從未公開。
  書中的流量數字、拆分順序、故障情境，都是為了教學而設計的**合理化重構**。
- 第六篇（第十四～十七章）涉及 2025–2026 的新產品與新名詞，
  雲廠商的產品能力與命名變動極快，**請以官方文件的當前版本為準**，本書只負責講清楚
  「它想解決哪個老問題」。
- 所有廠商名稱、產品名稱屬於各自持有者，本書僅作技術討論之用。

## 一頁看完全書：14 次演進的痛點鏈

| # | 演進動作 | 觸發它的痛 | 章節 |
|---|---|---|---|
| 1 | 單機部署 Tomcat + MySQL | （起點） | 1.1 |
| 2 | 應用與資料庫分機部署 | 兩者搶 CPU/記憶體/磁碟 | 1.2 |
| 3 | 引入本地快取與分散式快取 | 讀請求把 DB 打爆 | 2.1–2.2 |
| 4 | 應用多副本 + 反向代理 | 單台應用 CPU 打滿 | 3.1–3.2 |
| 5 | 資料庫讀寫分離 | 快取擋不住的讀仍壓垮主庫 | 4.1 |
| 6 | 按業務垂直分庫 | 熱門業務吃光 DB 資源 | 4.2 |
| 7 | 大表水平拆分 | 單表破億，索引失效 | 4.3 |
| 8 | LVS / F5 扛 Nginx 集群 | Nginx 自己成為瓶頸 | 3.3 |
| 9 | DNS 輪詢 + CDN 多機房 | 單一機房頻寬與地理延遲 | 3.4 |
| 10 | 引入 NoSQL 與搜尋引擎 | 全文檢索、海量日誌 RDB 做不動 | 6.1 |
| 11 | 大應用拆小應用 | 一次發版全站停機 | 5.1 |
| 12 | 公共模組抽為微服務 | 同一段邏輯在八個系統各改一次 | 5.2 |
| 13 | ESB / API Gateway | 服務間協議與鑑權各自為政 | 6.3 |
| 14 | 容器化 + 容器編排 | **環境不一致 + 擴容靠人肉** | 7–11 |
| 15+ | Serverless / FinOps / AI 原生 | 資源利用率與 AI 負載 | 12–17 |

> 第 14 步是全書的樞紐。前 13 步是「把系統拆開」，第 14 步是「把拆開的東西重新管起來」。
> 如果你只想知道 Docker 與 K8s 為什麼存在，看懂第 11、12、14 步就夠了。
